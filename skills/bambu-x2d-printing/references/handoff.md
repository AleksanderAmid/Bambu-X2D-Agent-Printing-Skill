# Human approval at the Windows X2D

The installed Bambu connector supports X2D slicing and offline inspection on Windows. Its native X2D dispatch helper targets other operating systems. Use Bambu Studio for the Windows print handoff. Registration of a tool named `print_3mf`, a generic capability flag, or a successful offline receipt does not establish a Windows dispatch path.

## Prepare the review

1. Store the sliced plate in the job folder and inspect those exact bytes with `inspect_print_file`. Keep its structured result (or parse its text JSON). If needed, run `python scripts/plate_review.py "job/part.gcode.3mf" "job/receipt.json" --studio-plate 1` from the skill directory. It compares the file SHA-256, byte length, machine and selected plate with the receipt. The script has no printer I/O and cannot authorize a print.
2. Open the verified copy in Bambu Studio when the user wants to print or see the preview. Preserve any unrelated unsaved job. Inspect the selected plate's parts, first layer, transitions, profile settings and warnings. Staging the preview is sufficient for a slice-only request. Use the supported Studio UI for any needed configuration. If the app re-slices or substitutes an artifact, save and inspect that version before relying on earlier approval.
3. Show the operator the part, quantity, target printer as identified in Studio, plate number/name, preview, nozzle pair, bed, process and material-to-nozzle/AMS or external-spool mapping, estimated time and filament, plus relevant uncertainties. Explain what was verified from the file versus by the operator or fresh telemetry. If the physical setup differs, resolve it before the final control. The operator can verify the bed is clear and the correct surface and material are installed.
4. Keep the file hash and selection with the review. Bind any chat authorization to the specific saved plate, printer, mapping, quantity and settings just presented. A general request to design, slice or print starts preparation. It does not approve a subsequently created, unseen plate.

## Complete one of two routes

For a repeatable pre-click check, use `python scripts/handoff_check.py plate.gcode.3mf receipt.json context.json`. The context has four keys. `review` records the job shown to the human and `visible` records the current, independently verified selection. Both include `sha256`, one-based `studio_plate`, `printer`, `quantity`, `nozzles_mm`, `plate_type`, a specific `mapping` (project material and physical tray or external spool), and a `print_options` object for relevant dialog selections. Use the receipt's canonical bed type, e.g. `textured_plate`. Bind the visible artifact to the actual opened file and recompute its hash locally. Set `visible.final_control_verified` only after recognizing the intended final control. If the open artifact or settings cannot be established, leave the click to the operator.

The other keys record actual events. `operator_action` can be `human_click`, `approved_and_delegated` or `prepare_only`. Only an explicit, current human instruction justifies the delegated value. `previous_start` begins at `none`. Record `attempted` before making a click and keep `unknown` if the result is uncertain. Record observed acceptance/running or a rejection. Keep that record across interruptions. The helper compares the evidence you supply. It is stateless and has no access to chat authorization or printer controls. Never generate the visible selection by copying the review.

| Operator action after review | Agent action | Completion evidence |
|---|---|---|
| Operator wants the final click | Leave Studio at preview or the verified final dialog. Let the human operate Print/Send. | Report prepared or awaiting operator. Report started only if observed. |
| Operator explicitly approves the reviewed job **and asks the agent to send it** | With trusted desktop control, recheck the file identity, visible final dialog, selected device, plate and current mapping. Click the identified start control once. | Check Studio's job/device status or authorized read-only telemetry for that job. Report accepted, observed running, rejected, or uncertain as supported. |
| The operator cancels, the target changes, or the click outcome is uncertain | Leave the job pending. After an ambiguous click check the device queue and active job, and have the operator resolve uncertainty before another start. | Keep the reviewed artifact, changes, last observed state and outstanding decision. |

Studio distinguishes sending a file to storage from sending a job that starts printing. Read the actual dialog and action label for the installed version. A storage upload does not establish that printing began. Do not attempt to obtain equivalent motion through a raw bridge, a printer-file command, heating, a generic print helper or an alternate model identity. A headless client without trusted UI control can hand the exact file and review to the operator.

If a print is already running and the user requests status, read the supported status or camera interface. A camera frame can establish visible deposition or a visible problem. It cannot certify bore diameter or completed assembly fit. The server's persistent record covers jobs it independently observed or dispatched according to that tool's contract. For a Studio-launched job verify identity before attributing a record. Treat pause, resume, cancel, heater changes and error clearing as separate hardware operations with their own requested intent. A firmware completion message records execution. Physical fit requires physical evidence.
